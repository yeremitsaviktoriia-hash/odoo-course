## Структура зв’язків

Book описує видання, Copy — його фізичний примірник, Member — читача, а Loan — видачу конкретного примірника конкретному читачеві. Це дає змогу вести окрему історію кожного примірника одного видання.

| Прямий зв’язок (`Many2one`) | Зворотний зв’язок (`One2many`) | Чому поле обов’язкове і діє `ondelete='restrict'` |
| --- | --- | --- |
| `Copy.book_id → Book` | `Book.copy_ids` показує всі примірники видання | Кожен примірник належить виданню. Odoo блокує видалення книги, поки на неї посилаються примірники. |
| `Loan.copy_id → Copy` | `Copy.loan_ids` показує історію видач примірника | Кожна видача стосується конкретного примірника. Odoo блокує видалення примірника, поки на нього посилаються видачі, зокрема повернені. |
| `Loan.member_id → Member` | `Member.loan_ids` показує історію видач читача | Кожна видача має читача. Odoo блокує видалення читача, поки на нього посилаються видачі. |

`One2many` використовує відповідне зворотне поле `Many2one`. Назву книги й автора у формі видачі Odoo бере через `copy_id.book_id`, а номер читацького квитка — через `member_id`.

## Практичне заняття 3. Бізнес-логіка видач

Термін видачі становить **14 календарних днів** від дати видачі. Якщо примірник фактично повернули після терміну, штраф становить **5 грн за кожен день прострочення**. За повернення вчасно або за відсутності дати повернення штраф дорівнює нулю. Тривалість і ставку задано по одному разу у відповідних методах обчислення в [моделі видачі](custom_addons/library_rental/models/loan.py).

### Серверні обмеження

Усі три перевірки піднімають `ValidationError` із повідомленням українською.

| Обмеження | Якій бізнес-помилці запобігає |
| --- | --- |
| `@api.constrains('copy_id', 'state')` шукає іншу активну видачу того самого примірника та виключає ID поточного запису | Один фізичний примірник не можна видати повторно, поки попередня видача активна. Виключення ID дозволяє зберігати зміни в самій активній видачі. |
| `@api.constrains('loan_date', 'due_date')` вимагає, щоб заповнений термін був строго пізнішим за дату видачі | Неможливо задати нульовий або від’ємний строк видачі. |
| `@api.constrains('loan_date', 'return_date')` вимагає, щоб заповнена дата повернення була не ранішою за дату видачі | Історія не може показувати повернення примірника до того, як його видали. Повернення в день видачі допустиме. |

Під час вибору зайнятого примірника `onchange` показує попередження у формі. Серверне обмеження перевіряє конфлікт під час збереження через ORM. Поточна перевірка через пошук покриває послідовні операції. Гарантія для паралельних транзакцій потребує обмеження на рівні бази даних.

### AI-рев’ю та ручні виправлення

Під час рев’ю виправлень у compute-методах не знадобилося. У `_compute_due_date` уже було `@api.depends('loan_date')`, а в `_compute_fine_amount` — `@api.depends('due_date', 'return_date')`. Обидва поля вже мали `store=True`. Динамічне поле `is_overdue` обчислюється під час читання списку.

В Odoo shell зміна `return_date` автоматично збільшила штраф із 0 до 15 грн. Після зміни `loan_date` термін пересунувся з 15.11.2026 на 17.11.2026, а штраф зменшився до 5 грн. Очищення `return_date` обнулило штраф. Також перевірено, що `onchange` повертає лише `warning`, поточна видача зберігається, а друга активна видача відхиляється. Тестову транзакцію відкочено.

Під час переходу до обчислюваного терміну прибрано ручні значення `due_date` з демо-даних і додано міграцію для перерахунку термінів у наявних видачах.
